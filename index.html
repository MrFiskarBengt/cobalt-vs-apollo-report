A focused implementation comparison

Apollo + TypeGraphQL vs Cobalt

Two implementations of a small, authenticated application. Both use Bun, the same data functions, and the same React views. The comparison asks what changes when TypeScript resolvers define the GraphQL schema.

Both servers run on Bun Shared MongoDB data and access rules User and record operations

Summary

Cobalt reduces schema-definition steps. The speed results are mixed.

Warm API times were close. Cobalt's process startup took longer, while its client generation and browser flow had lower median times. The browser measurements have small sample sizes and use development mode.

03 · What changes in code

One explicit schema layer versus typed operations

Apollo keeps the GraphQL contract visible in decorators and resolver methods. Cobalt uses each operation's TypeScript input and return types to infer that contract.

Apollo · schema and resolver are separate declarations 
@ObjectType()
class Item {
  @Field(() => String) id!: string
  @Field(() => String) name!: string
}
Apollo · resolver
@Authorized(/* allowed roles */)
@Query(() => [Item])
items(@Ctx() context: Context) {
  return listItems(context.user)
}
This illustrative example declares the GraphQL fields and resolver authorization explicitly; implementation names are generalized.
Cobalt · operation types form the schema source 
export async function Query(): Promise<Item[]> {
  const context = $$ctx(this)
  return listItems(context.user)
}
The TypeScript operation signature is used to infer the GraphQL contract and generate the client SDK.

04 · Findings

Implementation trade-offs

Area Apollo + TypeGraphQL Cobalt Assessment
Server contract Decorated output/input classes plus resolver methods and registration. Typed operation functions; schema and SDK are generated from them. Less schema boilerplate with Cobalt; Apollo makes each contract choice explicit.
Client setup Apollo Client includes React hooks, normalized caching, and mutation/refetch behavior. Cobalt provides the SDK; TanStack Query supplies React hooks, caching, and invalidation. Apollo uses one client package for GraphQL, hooks, and cache. Cobalt adds a separate query/cache layer; query usage is similar once hooks exist.
Change surface A change can touch schema, resolver, document, generated operation types, and tests. A change can touch the operation/domain type, generated SDK, query hook, and tests. Cobalt removes a schema authoring step. The effect on real change time remains unmeasured.
Regression checks Schema validation, generated operation types, and parity tests. Generated SDK types and the same behavior/parity tests. All 12 comparison integration tests pass. This supports the scoped behavior, not broader coverage.
Debugging Explicit schema and mature GraphQL/Apollo tooling. Operations stay close to TypeScript; generated schema and SDK add framework-specific artifacts. Both are debuggable; the failure path and time-to-diagnose need a measured exercise.
Performance Direct warm p50: 2.3–4.0 ms; p95: 3.2–5.9 ms. Direct warm p50: 2.3–4.0 ms; p95: 3.1–6.0 ms. Medians are close; p95 varies by operation. The measurements do not establish an overall API speed advantage.

05 · Security and scope

The important user checks are shared; HTTP controls differ

Both services authenticate requests and enforce server-side access rules. The initial HTML includes a partial user for quick display and is marked no-store; each client refreshes the user in the background.

Controls in this local comparison

  • Both APIs listen on loopback and require the expected same-origin request.
  • Both authenticate requests and reload user information.
  • Both enforce the same authorization rules.
  • Apollo requires persisted operations, caps JSON bodies, and applies depth/complexity limits.
  • Cobalt applies same-origin, a 32 KB body cap, introspection blocking, and 401 responses for expired sessions.

Known boundary

Cobalt's CLI does not expose Apollo-equivalent persisted-query, depth, or complexity controls. The Cobalt guard is a small local Bun adapter, and the service is loopback-only. This prototype is not a production deployment or a security audit.

The test identity header is enabled only in the explicitly configured local end-to-end test mode.

07 · Conclusion

Interpretation

Cobalt uses fewer schema declarations. API medians are close; startup and browser measurements differ.

The results describe this implementation and fixture. Cobalt had a longer startup median and a shorter client generation median. Direct API medians were close; browser medians were lower for Cobalt, with substantial variation in a small sample. Change effort and debugging time have not been measured.
